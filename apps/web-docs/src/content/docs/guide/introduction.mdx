**BlaC** (_Business Logic Components_) is a state management library for React and TypeScript. You write state, and the logic that changes it, as plain classes called Cubits. Components use them through one hook, `useBloc`.

```tsx twoslash
import React from 'react';
import { Cubit } from '@blac/core';
import { useBloc } from '@blac/react';

class CounterCubit extends Cubit<{ count: number }> {
  constructor() {
    super({ count: 0 });
  }
  increment = () => this.emit({ count: this.state.count + 1 });
}

function Counter() {
  const [state, counter] = useBloc(CounterCubit);
  return <button onClick={counter.increment}>Count: {state.count}</button>;
}
```

That is the whole setup. There is no store to configure, no provider to wrap the app in, and no reducer or selector to write.

## What it does for you

**Keeps logic out of components.** A Cubit holds state, derived values (getters), validation and async work. It has no React dependency, so it runs in a plain unit test and can be reused outside React. Components render state and call methods. [Architecture & Philosophy](/docs/guide/philosophy/) explains why this split pays off.

**Re-renders only what read the change.** During render, `useBloc` hands the component a proxy that records which values it reads. The component re-renders when one of those values changes, and other state changes never reach it. Below, two components share one Cubit and each reads a different field. **Manages instances.** A registry creates a Cubit the first time a component asks for it, shares it with every other component that asks, and disposes it when the last one unmounts. Pass `args` for one instance per key, mark a class `isolated` for one instance per mount, or `keepAlive` to keep it after the last unmount.

**Types flow through.** State, methods and `args` are typed from the class itself, so `useBloc` needs no type annotations.

## Packages

| Package                | What it gives you                                                      |
| ---------------------- | ---------------------------------------------------------------------- |
| `@blac/core`           | `Cubit`, the registry, `watch()`, cross-bloc tracking, plugins. No React. |
| `@blac/react`          | `useBloc`, `BlocProvider`, `RegistryProvider`, and testing helpers.    |
| `@blac/async`          | `resource()`, `mutation()` and tag-based `invalidate()`, kept in state. |
| `@blac/plugin-persist` | Persist state to IndexedDB or Web Storage.                             |
| `@blac/devtools-*`     | An in-app panel and a Chrome DevTools extension.                       |
| `@blac/logging-plugin` | Structured logs of state changes.                                      |

<details>
<summary>Under the hood: DirtyTalk</summary>

The change tracking (path-based dirty tracking, the render-time proxy, batched flushing) lives in a lower-level, framework-agnostic family of packages called [DirtyTalk](https://dirtytalk.42.dog/). BlaC's `StateContainer` extends `@dirtytalk/structural`'s container. You never need to use it directly.

</details>

## How it compares

| Library           | Where logic lives        | What decides re-renders                       | Lifecycle and sharing                                       |
| ----------------- | ------------------------ | --------------------------------------------- | ----------------------------------------------------------- |
| **BlaC**          | Typed `Cubit` classes    | Values read during render, recorded by a proxy | Ref-counted registry: shared, keyed, isolated or kept alive |
| **Zustand**       | Store creator function   | A selector per hook (`useStore(s => s.x)`)    | Module singleton, or a store in context                     |
| **Redux Toolkit** | Slices, reducers, thunks | `useSelector`, often with `createSelector`    | One global store in `<Provider>`                            |
| **MobX**          | Observable classes       | Observables read inside `observer()`          | You create instances; share them through context            |
| **Jotai**         | Small composed atoms     | A subscription per atom                       | Provider, or the default store                              |

[Mental Model](/docs/guide/mental-model/#honest-comparisons) has the longer comparison, including when another library is the better fit.

## When to use it

BlaC fits when:

- State is **shared** by several components, without prop drilling or provider trees.
- There is **real business logic**, such as validation, multi-step flows or derived values, that belongs in a testable class rather than spread across hooks.
- You want **fast unit tests** of that logic, without mounting React.

:::tip[When you don't need it]
State that lives in one component and has no rules behind it, such as whether a menu is open, belongs in `useState`. BlaC and `useState` work side by side.
:::
