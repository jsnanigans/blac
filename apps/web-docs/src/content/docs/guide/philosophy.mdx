Components tend to grow. One starts out rendering a button, and a few features later it holds `useState`, three `useEffect`s, a `fetch`, validation rules and a loading flag, all before the `return (`.

BlaC is built on one premise: **components shouldn't own business logic, and business logic shouldn't depend on the UI framework.**

## The problem with "fat components"

When state, logic and data fetching all live in components and custom hooks:

- **Components do too many jobs.** Besides turning state into markup, they orchestrate async flows, guard against stale closures and compute derived flags.
- **Re-renders become your job.** `useMemo`, `useCallback` and hand-written selectors spread through the code to keep unrelated views from re-rendering.
- **Testing needs a DOM.** Checking a validation rule or a checkout flow means mounting a component tree, mocking providers and clicking simulated buttons.
- **The logic is tied to the view library.** Reusing a feature in React Native or a script means untangling it from hooks first.

## Three layers: UI, Logic and Data

BlaC splits an application into three layers, each with one job:

<CardGrid>
  <Card title="1. The UI Layer" tone="rose">
    **Renders state and forwards interactions.** Components turn state into
    markup and call methods from `onClick`, `onChange` or `onSubmit`. They never
    talk to the Data layer directly.
  </Card>
  <Card title="2. The Logic Layer (The Core)" tone="cobalt">
    **Where the application lives.** `Cubit` classes hold state, validate
    input, derive values, coordinate features and call the Data layer. They
    don't depend on React or the DOM.
  </Card>
  <Card title="3. The Data Layer" tone="cable">
    **Moves data in and out.** REST, GraphQL, IndexedDB, `localStorage` or an
    in-memory fake for tests. The Logic layer doesn't care how data is stored,
    and the UI doesn't know this layer exists.
  </Card>
</CardGrid>

## The one-way rule: UI never touches Data

The boundary that matters most: **nothing travels between UI and Data without passing through the Logic layer.** Components call methods; methods call the API; state flows back to the components that read it.

Here is a checkout flow split that way:

```tsx twoslash
import React from 'react';
import { Cubit } from '@blac/core';
import { useBloc } from '@blac/react';

interface OrderItem {
  id: string;
  price: number;
  qty: number;
}

// ── 3. DATA LAYER: plain functions or clients (REST, GraphQL, memory) ──
const orderApi = {
  async submitOrder(items: OrderItem[]): Promise<{ orderId: string }> {
    return { orderId: 'ord_123' };
  },
};

// ── 2. LOGIC LAYER: pure TypeScript class, zero React imports ──
interface CheckoutState {
  items: OrderItem[];
  status: 'idle' | 'submitting' | 'confirmed' | 'error';
  orderId: string | null;
}

export class CheckoutCubit extends Cubit<CheckoutState> {
  constructor(private api = orderApi) {
    super({ items: [], status: 'idle', orderId: null });
  }

  get total(): number {
    return this.state.items.reduce((sum, i) => sum + i.price * i.qty, 0);
  }

  get canSubmit(): boolean {
    return this.state.items.length > 0 && this.state.status !== 'submitting';
  }

  submit = async () => {
    if (!this.canSubmit) return;
    this.patch({ status: 'submitting' });
    try {
      const { orderId } = await this.api.submitOrder(this.state.items);
      this.patch({ status: 'confirmed', orderId, items: [] });
    } catch {
      this.patch({ status: 'error' });
    }
  };
}

// ── 1. UI LAYER: takes state, renders markup, wires callbacks ──
export function CheckoutSummary() {
  const [state, checkout] = useBloc(CheckoutCubit);

  return (
    <section>
      <p>Total: ${checkout.total.toFixed(2)}</p>
      <button disabled={!checkout.canSubmit} onClick={checkout.submit}>
        {state.status === 'submitting' ? 'Placing order…' : 'Place order'}
      </button>
      {state.orderId && <p>Order #{state.orderId} confirmed!</p>}
    </section>
  );
}
```

Look at `CheckoutSummary` at the bottom:

- It has **no business logic.** It doesn't compute the total, decide whether submitting is allowed, or handle network errors.
- It has **no selectors.** The render-time proxy records that it read `checkout.total`, `checkout.canSubmit`, `state.status` and `state.orderId`, and re-renders it when one of those changes.
- It knows **how to render** the current state and **which method to call**. Nothing else.

## Why this pays off

### 1. The UI can change

`@blac/core` has no React dependency, so a Cubit runs anywhere JavaScript does:

- **React and React Native:** `useBloc(CheckoutCubit)`, with the same class.
- **Scripts, servers and workers:** drive the class with [`acquire()`](/docs/core/instance-management) and [`watch()`](/docs/core/watch). See [Using BlaC outside React](/docs/integrations/outside-react).
- **Other view libraries:** a small adapter around `watch()` connects them, and the Logic and Data layers stay as they are.

### 2. The data source can change

The Logic layer calls plain functions or interfaces, like `orderApi` above. Storage that applies to many blocs, such as IndexedDB or `localStorage`, attaches from outside as a [plugin](/docs/plugins/persistence):

- Prototype against an in-memory fake.
- Switch to REST or GraphQL when the backend is ready, by changing the API module.
- Add persistence with [`@blac/plugin-persist`](/docs/plugins/persistence) without changing components.

### 3. Logic is tested without rendering

When the logic lives in a class, a test constructs it, calls methods and checks state. No React tree, no `act()`, no simulated browser:

```ts twoslash
import { Cubit } from '@blac/core';

interface OrderItem {
  id: string;
  price: number;
  qty: number;
}
interface CheckoutState {
  items: OrderItem[];
  status: 'idle' | 'submitting' | 'confirmed' | 'error';
  orderId: string | null;
}
class CheckoutCubit extends Cubit<CheckoutState> {
  constructor(
    private api: {
      submitOrder(items: OrderItem[]): Promise<{ orderId: string }>;
    },
  ) {
    super({ items: [], status: 'idle', orderId: null });
  }
  get total(): number {
    return this.state.items.reduce((sum, i) => sum + i.price * i.qty, 0);
  }
  get canSubmit(): boolean {
    return this.state.items.length > 0 && this.state.status !== 'submitting';
  }
  submit = async () => {
    const { orderId } = await this.api.submitOrder(this.state.items);
    this.patch({ status: 'confirmed', orderId, items: [] });
  };
}
// ---cut---
// The whole checkout flow, tested without a DOM:
const fakeApi = {
  submitOrder: async () => ({ orderId: 'test_99' }),
};

const checkout = new CheckoutCubit(fakeApi);
checkout.patch({ items: [{ id: '1', price: 25, qty: 2 }] });

console.assert(checkout.total === 50);
console.assert(checkout.canSubmit === true);

await checkout.submit();

console.assert(checkout.state.status === 'confirmed');
console.assert(checkout.state.orderId === 'test_99');
```

When you do test a component, [`renderWithBloc`](/docs/testing/react) mounts it with the state you choose, so you don't mock `fetch` or replay user steps to reach that state.

## Pragmatism over dogma

The three layers are a tool, not a rule:

- **Local UI state is fine.** Whether a dropdown is open can stay in `useState` if nothing else cares.
- **No ceremony for small things.** A feature doesn't need interfaces, factories and three files. One Cubit next to the component already separates the logic and makes it testable.
- **Grow when it helps.** Start with one Cubit. Later, move API calls into a data module, compose blocs with [`depend()`](/docs/core/bloc-communication), or use [`@blac/async`](/docs/guide/async-resources/) for request cancellation and invalidation.
